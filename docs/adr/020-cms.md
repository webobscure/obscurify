# ADR-020: CMS — Reuse the Theme Engine's Versioning and Section Model, Don't Fork It

## Status
Accepted

## Context
Milestone 14 needed pages, navigation, a blog, SEO metadata, and
redirects, built directly on top of Milestone 13's theme engine (ADR-019).
Three design questions mattered most: whether a CMS page needs its own
content model or can reuse the theme engine's section/block system;
whether a page needs a "starting template" concept and, if so, how
tightly that couples to theme versioning; and whether a blog post needs
the same draft/publish/rollback machinery a page does.

## Options

**Page content model:**
1. A page has its own content type — e.g. a single rich-text/HTML body
   field, independent of `ThemeSection`/`ThemeBlock`.
2. A page's content is the exact same section-instance array shape
   `ThemeTemplate.sections` already uses, resolved against the active
   theme version's section/block *type* definitions through the same
   `ThemeRenderer` — no second content model, no second renderer.

**"Starting template" for a new page:**
1. `PageTemplate` is scoped to a specific `ThemeVersion`, the same way
   `ThemeSection`/`ThemeBlock` are — a page's chosen template is a live
   foreign key into that theme version's own template rows.
2. `PageTemplate` is a plain, store-scoped preset — its `sections` are
   copied into a new `PageVersion` once, at creation time, and never
   referenced again.

**Blog post lifecycle:**
1. `BlogPost`/`PostVersion`, mirroring `Page`/`PageVersion` exactly —
   draft/publish/rollback for every post.
2. `BlogPost` is one mutable row; `status`
   (draft/published/scheduled/archived) is the entire lifecycle, no
   version history, no rollback.

## Decision

**Page content: Option 2.** Option 1 would mean two parallel rendering
paths (one for theme templates, one for page bodies) and two parallel
places a merchant learns to configure content. Reusing the exact
instance shape and delegating to `ThemeRenderer` cost one new public
method (`renderCmsPage()`) and one extracted private helper
(`renderVersion()`, factored out of the existing `render()` so both
paths share one merge implementation) — verified safe by rerunning
`tests/Feature/Themes/*` unchanged immediately after the refactor before
writing anything CMS-specific. The one-way dependency stays intact:
`ThemeRenderer` accepts a raw section array and returns a `RenderedPage`
without ever importing anything from `App\Domain\Cms`.

**PageTemplate: Option 2.** Option 1 was rejected during design, before
any code was written, once its consequence became clear: a `PageVersion`
is supposed to be an immutable snapshot once published (`assertEditable()`
enforces this for `sections` and SEO both) — but a live FK to a
`ThemeVersion`'s own template row would let that theme version's owner
edit content out from under an already-published page, or leave the FK
dangling the moment a theme's draft is superseded by publish/rollback/
duplicate (which clone `ThemeSection`/`ThemeBlock`/`ThemeTemplate` into
new rows with new ids — see `CloneThemeVersionContent`). Copy-once
sidesteps both problems entirely: nothing about a `PageTemplate` being
edited or deleted can ever retroactively affect a page that started from
it, because after creation there's no relationship left to affect.

**Blog post: Option 2.** The spec draws a real line here — versioned,
rollback-capable content is a *page* concern (Shopify-style "theme
customization can be undone"), while a blog post's `status` states
(draft/published/**scheduled**/archived) are a simpler, single-row
workflow with no rollback requirement. Building `PostVersion` would mean
extending `ClonePageVersionContent`-style content-cloning to a domain
that never asked for it, for a milestone that explicitly scoped blog
posts by status alone.

## Consequences

### Positive
- Zero duplicate section/block rendering logic — a "hero" section a
  theme's home page uses is usable on a CMS page with no adapter, no
  translation layer, and no risk of the two diverging.
- A `PageTemplate` can be freely edited or deleted without an audit of
  every page that ever used it as a starting point — there is nothing
  left to break.
- Pages get real rollback (verified in `PageLifecycleTest`'s rollback
  test, structurally identical to `ThemeLifecycleTest`'s) at the exact
  incremental cost ADR-019 already paid for themes — `ActivePageVersion`
  cost one migration + one model, not a new state-machine design.

### Negative
- `PageTemplate` cannot express "this page's layout should stay in sync
  with the template it was created from" — a merchant who wants that
  has to manually re-copy sections. Accepted: that's a materially
  different feature (a live, tracked relationship) than what this
  milestone needed, and the copy-once model is what keeps published
  pages genuinely immutable.
- A page's content is entirely dependent on the store's *currently
  active* theme having matching section handles — if a merchant
  switches themes, an existing page's `sections` referencing
  handles the old theme defined but the new one doesn't will silently
  drop those sections at render time (`ThemeRenderer::resolveSection()`
  already does this leniently, dropping an unknown handle rather than
  erroring — the same behavior a template referencing a stale handle
  already has). Not fixed in this milestone; flagged as a real,
  inherited limitation rather than a new one this design introduced.
- Blog posts having no version history means there is no built-in way
  to undo a published post's edit — accepted as the direct, intended
  consequence of the scope line drawn above, not an oversight.

## Security Requirements
- Every Cms table (`Page`, `PageVersion`, `ActivePageVersion`,
  `PageTemplate`, `Menu`, `MenuItem`, `Author`, `Blog`, `BlogPost`,
  `SeoMetadata`, `Redirect`) uses `BelongsToTenant`, verified with
  dedicated cross-tenant tests in every `tests/Feature/Cms/*.php` file —
  Store A can never read, edit, publish, duplicate, or roll back a
  Store B page, menu, blog, post, or redirect.
- `PageVersionSeoController`/`BlogPostSeoController`'s `Rule::exists()`
  checks for `author_id` are explicitly scoped by `store_id` — a raw
  `Rule::exists()` query bypasses Eloquent's `BelongsToTenant` global
  scope entirely (it isn't an Eloquent query), so an unscoped check
  would let a request attach another store's `Author` row to a post;
  caught and fixed during this milestone's own review before merge, not
  by a test failure.
- `StorefrontPageController`/`StorefrontBlogController` sit behind
  `storefront.tenant` only, never `auth:sanctum` — the same structural
  "no session exists that could ever request a draft" guarantee
  `StorefrontThemeController` already has. A page's draft-preview
  equivalent is exclusively the admin-authenticated
  `PageController::preview`.
