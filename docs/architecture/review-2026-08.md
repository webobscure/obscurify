# Architecture Health Review — 2026-08

**Scope:** full codebase review after Milestones 1–4 (Foundation, Catalog, Cart/Checkout/Orders, Payment Foundation) and the merchant-admin shell redesign. Read-only investigation except for two Critical and two obvious-High fixes applied and documented below (per the review's own guardrails: no rewrites, no microservices migration, no architecture changes without a concrete demonstrated problem).

**Bottom line: the architecture is healthy.** The modular-monolith boundaries, tenant-isolation trait, transactional-outbox pattern, payment-provider abstraction, and admin/storefront API separation are all still doing their jobs after four milestones of real feature growth — none of that needed to change. The debt that exists is concentrated in two places that don't require touching working architecture to fix: **security configuration that fails open under plausible misconfiguration** (two of which are now fixed), and **operational completeness that was never finished** (no scheduler, almost no logging). See [`technical-debt.md`](technical-debt.md) for the full itemized list (47 findings, 2 Critical + 2 High already fixed).

## 1. Current architecture

```text
                        ┌─────────────────────────┐
                        │   Nuxt Merchant Admin    │  apps/admin — bearer-token
                        │   (apps/admin, :3000)    │  auth (ADR-011), SPA
                        └────────────┬─────────────┘
                                     │ Authorization: Bearer <token>
                                     │ via packages/api-client
┌───────────────────────┐           ▼            ┌──────────────────────────┐
│   Nuxt Storefront      │  ┌─────────────────┐   │  Laravel API (apps/api)  │
│  (apps/storefront)     │─▶│  api/v1/*        │◀──┤  modular monolith        │
│  guest-cart cookie,    │  │  auth:sanctum    │   │  (see module map below)  │
│  CORS + credentials    │  │  admin surface   │   └──────────────┬───────────┘
└───────────┬─────────────┘  ├─────────────────┤                  │
            │                │  api/v1/        │                  ▼
            │ Host-resolved  │  storefront/*   │        ┌──────────────────┐
            └───────────────▶│  storefront.    │        │   PostgreSQL      │
                             │  tenant          │        │  shared schema,   │
                             ├─────────────────┤        │  store_id on every │
                             │  payments/       │        │  tenant table      │
                             │  webhooks/*      │        └──────────────────┘
                             │  no auth —       │
                             │  HMAC-verified    │        ┌──────────────────┐
                             └─────────────────┘        │      Redis         │
                                                          │  sessions, queue,  │
                                                          │  Horizon (default  │
                                                          │  queue only — see  │
                                                          │  TD-9)             │
                                                          └──────────────────┘
```

Three independent authentication/authorization boundaries, each appropriate to its caller and verified to actually be enforced (not just documented) during this review:

- **Admin → API**: Sanctum bearer token (ADR-011), `auth:sanctum` middleware, `EnsureTenantContext` establishes `TenantContext` from an active `StoreUser` membership.
- **Storefront → API**: no user auth (guests); `EnsureStorefrontTenantContext` resolves `TenantContext` from the request `Host` header against `domains`; a separate `HttpOnly` cart cookie scopes cart/checkout ownership. (TD-22: `Host` itself isn't validated against a trusted-host allowlist — see technical-debt.md.)
- **Payment provider → API**: no user/session auth at all — HMAC-SHA256 signature verification (`hash_equals`, correct order, verified before any DB access) plus a claim/poll idempotency protocol against `(provider, external_event_id)`, genuinely backed by real two-process concurrency tests (`pcntl_fork`-based — confirmed by reading `tests/Pest.php`'s `runConcurrently` helper, not just trusting the commit message).

Still unimplemented (long-term map in `ARCHITECTURE.md` §5, unchanged by this review — nothing here needed correction, just confirmation it's still accurate): Staff/Permissions (beyond the unused role column), Pricing, Discounts, Checkout beyond guest, Refunds, Fulfillment, **Shipping**, Themes, Pages, Navigation, Notifications, Integrations, Webhooks-as-a-feature, Apps, Billing, Plans, Subscriptions, Analytics, Audit, Platform Administration.

### Module coupling — what was checked, what was found

Cross-domain imports were enumerated exhaustively (`grep` of every `use App\Domain\X\` across `app/Domain`). The pattern is overwhelmingly Eloquent relations to `Store` (expected — shared-schema multi-tenancy per ADR-005) and the `Storefront` module reading everywhere else as a pure read-facade (nothing imports *from* `Storefront` — confirmed). Two real, minor instances of direct cross-domain writes, both documented in technical-debt.md:

- **Payments → Orders**: `ProcessPaymentWebhook::applyTransition` directly calls `$order->update(['financial_status' => ...])` rather than going through an Orders-owned service (TD-31/46). Accepted by design — the docblock at the call site is explicit that this is the *only* place financial_status ever moves, and Payments is the correct owner of that transition. First cut point if Payments is ever extracted.
- **Catalog → Inventory**: `CreateProductVariant::handle` directly creates an `InventoryItem` row (TD-30). One call site today, contained, but not behind an Inventory-owned entry point — worth fixing before a second creator copies the pattern.

Neither rises to "accidental coupling" in the sense the review was checking for — both are single, documented, intentional decisions, not scattered reach-throughs.

## 3. Key invariants

Verified directly against the code, not inferred from comments:

- **Tenant isolation is systematic.** Every tenant-owned model uses `BelongsToTenant`, which adds a global scope on every query path (find/findOrFail/route binding/update/delete all go through `newQuery()`) and fails closed — `TenantContext::store()` throws if no tenant is active, it never silently returns unscoped data. `store_id` is never fillable; it's forced from `TenantContext` on `creating()`. The 5 uses of `withoutGlobalScopes()` in the codebase were individually checked: each occurs precisely where tenant context is *being determined* (domain resolution, webhook payment lookup before a store is known) or in an internal cron/console command explicitly re-scoping itself — none is a bypass.
- **Inventory: `available = on_hand - reserved`**, defined once on `InventoryLevel::available()`, but duplicated inline in `ReserveInventory` (TD-29) — the one place this should least be re-derived, since it's the concurrency-critical reservation path. `on_hand` is mutated only by `AdjustInventory`; `reserved` only by `ReserveInventory`/`ReleaseExpiredReservations`. Reservation locking (`lockForUpdate()` on `InventoryLevel` rows, split allocation across locations ordered by id, called only from within `CompleteCheckout`'s existing transaction) is correct and documented.
- **Order snapshots are immutable.** Verified by `OrderSnapshotImmutabilityTest`: editing a live `Product`/`Variant`/`Customer` after an order exists does not retroactively change `OrderItem`/`OrderAddress` — a genuinely good invariant test, not just an assumption.
- **The transactional outbox is genuinely atomic.** All three `RecordOutboxEvent::handle` call sites (`CompleteCheckout`, `CreatePayment`, `ProcessPaymentWebhook`) were traced individually and confirmed to execute inside the same `DB::transaction` as the domain state change they describe — the "committed but the event never got written" window is real closed, not just asserted in a comment. The consumer side (`outbox:process`) is deliberately minimal (proves atomicity, no real side effects yet) and — separately — was never scheduled to run (TD-8/32).
- **Payment provider abstraction holds.** Zero `instanceof` checks anywhere in `app/`. `Order`/`OrderController` have no provider dependency. Every provider-typed call goes through `PaymentProviderRegistry`. `FakePaymentProvider` is referenced in exactly 4 files, all inside the Payments module. The one violation (`SimulateFakePaymentWebhookJob` type-hints the concrete class, TD-20) is contained to a dev-only job.
- **Concurrency correctness is tested with real races, not mocks.** `tests/Concurrency/*` use `pcntl_fork` to run genuinely separate DB connections against the same rows — confirmed by reading the fork implementation in `tests/Pest.php`, not trusting the commit message. Covers payment creation idempotency, webhook delivery races, inventory reservation races, cart races.

## 4. Risks

Ranked by what would actually hurt, not by finding count — full detail in technical-debt.md.

1. **Silent-failure security defaults (TD-1, TD-2, TD-4 — two fixed, one fixed this review makes the pattern visible).** The cross-cutting theme the security review surfaced: *configuration that fails open when an environment variable is unset or misspelled*, rather than a bug in domain logic. Two instances were Critical and are now fixed; the same shape of guard (explicit allowlist, no silent defaults, boot-time assertion) is worth applying as a standing pattern before the next environment-dependent default is written, especially for the first real payment provider's secret.
2. **No scheduler at all (TD-8, TD-32).** Not hypothetical — `outbox:process` and `carts:prune-expired` are dead code in production right now, and `idempotency_keys` accumulates PII with no automatic pruning. This is the single highest-value fix left undone by this review's fix budget.
3. **No rate limiting beyond login (TD-6, TD-7, TD-16), no TrustProxies (TD-5).** Individually Medium/High; together they mean the platform has effectively no defense against volumetric abuse once it's behind a real load balancer, and the one rate limiter that exists (login) will misbehave (single shared bucket) the moment a proxy is introduced.
4. **Observability is not there yet (TD-9, TD-14).** Two log lines in the whole app. This isn't a risk of a bug — it's a risk that when a real incident happens (a merchant's payment doesn't reconcile), there will be nothing to look at.
5. **RBAC is schema-only (TD-27).** Not urgent today (every `StoreUser` is currently an `Owner`, no invite flow exists to create anything else), but it's the kind of gap that's much cheaper to close before multi-staff merchants exist than after.

## 5. Scalability concerns

Nothing here demands architectural change — these are the things worth watching as data volume grows, not blockers:

- **Missing `(store_id, created_at)` composite indexes** on `payments`, `inventory_items`, `products`, `collections` (TD-28) — all four have a list endpoint that filters by `store_id` and sorts by `created_at` with only a single-column index. Cheap migration, matters more per store as order/product volume grows. `orders` is fine — its `(store_id, number)` unique index happens to cover its actual list query.
- **`outbox:process` processes 100 rows per invocation with no backpressure signal** — fine at current volume, worth revisiting once it has real side effects and the schedule from TD-8 is in place (an everyMinute cron competing with itself if a run takes >60s needs a lock).
- **Redis holds both sessions and the queue** with no separate connection/eviction policy called out — not a problem yet, but worth a documented decision before Horizon queue pressure and session storage start competing for the same instance.
- **The webhook claim/poll protocol polls up to 100×20ms (2s) per crashed/stale claim (TD-44)** — fine at current webhook volume, would hold worker threads under load from a flaky provider.

## 6. Security concerns

Full findings in technical-debt.md (§12 items, TD-1/2/4/5/6/7/15/18/22/23/24/25/26/27/41/42/43/45). Headline, already stated above: the *domain logic* that was checked closely — webhook signature verification, tenant isolation, idempotency, outbox atomicity — is sound. The exposure is in configuration defaults and things that are simply missing (rate limits, trusted proxies/hosts, RBAC enforcement, token expiration). Two Critical and two High findings were fixed during this review (TD-1, TD-2, TD-3, TD-4); the rest are prioritized in technical-debt.md's summary table.

One explicit non-finding worth recording: the storefront CORS origin regex (`^https?://([a-z0-9-]+\.)?localhost:\d+$`) was tested against attacker-controlled origin strings (embedded dots, embedded newlines, `evil.com/x.localhost`) and found sound — no escaping bug, correctly anchored. The risk there was only ever the `*` + credentials combination (TD-4), now guarded against at boot.
